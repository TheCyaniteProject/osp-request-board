# How to Submit a Request

This is the request guide for the **Open Software Project**. If you have an idea for an open-source alternative to existing software (or for an entirely original software) you can submit it through the Request Board’s Issues page.

You do not need to be a developer or write a technical specification. Just explain the idea clearly enough for me to understand what you want, why it would be useful, and what its most important features would be.

## Before You Submit

Search the existing issues first. If someone has already requested the same software or a very similar idea, add your thoughts to that issue instead of opening a duplicate.

It is also worth checking whether a good open-source option already exists. I am interested in filling gaps, not recreating a healthy project that already does the job well.

## Rules

Please make sure your request follows these rules:

1. **Finished projects will be released to the public domain.**
   The source code and finished software I make through this project will be released to the public domain so that anyone can use, study, modify, build, and redistribute it.

2. **Requests for alternatives must fill a real gap.**
   A complete and actively maintained free or open-source alternative must not already be available. A request may still qualify if existing alternatives are abandoned, incomplete, no longer meaningfully updated, or missing important functionality.

3. **There must be enough reference material to research an existing program.**
   If you are requesting an alternative, include whatever public references are available: an official website, documentation, screenshots, reviews, demonstrations, YouTube videos, manuals, or similar material. I need to be able to understand what the original software does without access to its proprietary source code.

4. **The request cannot depend on copying protected material.**
   I can recreate useful ideas, workflows, and general functionality, but I will not copy proprietary source code, branding, trademarks, artwork, audio, or other copyrighted assets. The result needs to be its own program.

5. **The project cannot leave me with ongoing expenses.**
   The software must not require me to pay for a dedicated server, API access, hosting, storage, or another continuing service. Costs that can reasonably be handled by each user-such as supplying their own API key or self-hosting a server-are acceptable.

6. **The request must be reasonably clear.**
   You do not need to plan every screen or technical detail, but “make something useful” is not enough. Explain the problem, the intended users, and the core features that would make the software worthwhile.

7. **The official targets are Windows and Linux.**
   I will make official builds for Windows and Linux, with Linux releases provided as AppImages. The source code will be available, and users are welcome to make and share builds for other desktop platforms.

8. **Android requests must be simple.**
   I may take on requests for Android apps, but only when the project is relatively simple. Android development is not one of my specialties, so I will decide whether an Android request is within my ability and scope.

9. **Projects must be suitable for Node.js or C#.**
   All projects will be made with either Node.js-for command-line, web, or Electron applications-or C#, depending on the needs of the project. Requests that depend on a different language, framework, or platform-specific toolchain are outside the scope of this project.

10. **I will not accept game projects.**
    Games usually require a large amount of artwork, music, sound, animation, and other assets that can be expensive to produce. Because of that, this project is limited to non-game software.

11. **The request and resulting software must be legal.**
   I will not accept requests whose main purpose is illegal activity, bypassing access controls, invading privacy, distributing stolen material, or causing harm.

12. **A request is not a commission or a guarantee.**
   Submitting an issue does not mean I have agreed to build it. I may choose projects based on my interests, skills, available time, usefulness, scope, and the quality of the available references.

13. **Donations do not affect whether a request is accepted.**
   Donations support the project generally. They do not buy priority, guarantee that I will select an idea, or create an obligation to finish it by a particular date.

14. **Be respectful.**
    Questions, suggestions, and constructive discussion are welcome. Demands, harassment, spam, and repeated duplicate requests are not.

## Choosing a Request Type

Use one of these labels at the beginning of your issue title:

- `[Alternative]` for a free and open-source alternative to existing software
- `[Original]` for a new software idea that is not based on one particular program

For example:

- `[Alternative] Open-source alternative to ExampleApp`
- `[Original] Offline tool for organizing research notes`

## What to Include

Every request should include:

- **Summary:** What do you want me to make?
- **Problem:** What problem would it solve?
- **Intended users:** Who would use it?
- **Core features:** Which features are essential?
- **Optional features:** What would be nice to have, but is not necessary?
- **Target platforms:** Windows, Linux, Android, web, or something else? Remember that official desktop builds are limited to Windows and Linux.

If you are requesting an alternative, also include:

- The name and official link for the existing software
- Screenshots, videos, documentation, reviews, or other reference material
- The parts of the original software that matter most to you
- Any open-source alternatives you have already tried
- Why those alternatives do not meet your needs

For an original idea, examples of how someone would actually use the program are especially helpful. A short step-by-step use case often explains an idea better than a long feature list.

## Submit Your Request

Once you have read the rules and gathered your references, open a new issue on the Request Board, give it a clear title, and fill out the template as completely as you can.

I may ask follow-up questions or suggest changing the scope before deciding whether to take on the project. Even if I do not choose an idea, I appreciate the time you took to share it.
